# LongCodeZip 阅读笔记

## 文献信息

- **题目**：LongCodeZip: Compress Long Context for Code Language Models
- **作者**：Yuling Shi、Yichun Qian、Hongyu Zhang、Beijun Shen、Xiaodong Gu
- **版本**：arXiv:2510.00446v1，2025 年 10 月 1 日；Zotero 条目类型为 preprint，key：`TTNLH8LX`。本文依据该条目所附 13 页 PDF，不混用其他版本。
- **一句话概括**：先按任务指令从长代码中筛出相关函数，再把函数切成小块并按重要性分配 Token 预算，以减少下游代码模型需要处理的上下文。
- **论文入口**：[arXiv:2510.00446](https://arxiv.org/abs/2510.00446)；代码和数据入口见论文第 I 节的项目链接。

## 研究问题与贡献

**论文事实**：长代码上下文既增加推理延迟和 API 输入成本，也会让模型难以找到真正相关的信息。通用文本压缩忽略代码结构，单纯相似度检索可能漏掉词面不相似但对任务有用的内容（例如训练函数使用的配置类）。作者提出 LongCodeZip：免训练、可插拔的代码上下文压缩框架（第 I–II 节）。

**作者列出的贡献**（第 I 节）：

1. 函数级筛选后进行函数内块级剪枝的两阶段方法。
2. 按重要性分配预算，并用 0/1 背包选择块。
3. 在代码补全、模块摘要和仓库问答上评测，报告最高 5.6× 压缩比并称下游性能未受损。

## 输入、输出与处理流程

### 输入输出

输入包括任务指令 `q`、代码上下文 `c` 和 Token 预算 `B`。压缩结果是从原代码上下文中保留的子集／片段（未保留函数或内容以占位符表示）；随后将任务提示与压缩上下文交给下游生成模型。模型具体输出由任务决定：补全代码、生成摘要，或回答代码位置／函数检索问题（第 III-A、IV 节）。

### 阶段一：函数／类级粗筛

先沿函数或类边界切块。对候选代码片段 `c` 和任务指令 `q`，作者定义近似互信息：

```text
AMI(c, q) = PPL(q) − PPL(q | c)
```

其中 `PPL(q)` 是不提供片段时压缩器对指令的困惑度，`PPL(q|c)` 是提供片段后对指令的困惑度。困惑度下降越多，AMI 越高，片段越可能对当前任务有用。实际实现先按 AMI 排序，再在粗粒度预算内贪心纳入函数（第 III-A、III-C 节）。

这里的 AMI 是压缩模型的条件语言建模分数，不是从程序依赖图计算出的依赖强度，也不是“保留此代码必然能让任务正确”的概率。

### 阶段二：函数内部细筛

1. **按困惑度切块**：以代码行为原子单位；若某行的困惑度相对邻近行出现足够大的局部上升（阈值与全体行困惑度标准差和系数 `α` 有关），则把它视作新块边界。作者称这类边界能近似反映语义／结构转换（第 III-D 节）。
2. **按函数重要性分预算**：较高 AMI 的函数获得更多细粒度 Token。少于 5 行的小函数完整保留；大函数的基线保留率由剩余预算和总 Token 数计算，再按 AMI 调整并全局缩放（式 4–6）。参数 `β` 控制重要性倾斜程度。
3. **块级 0/1 背包**：每个块的“价值”是归一化 AMI，重量是 Token 数；在该函数预算内选价值总和最大的块。论文还提及保留集合 `P`，从剩余预算中先扣除已保留块（算法 2）。

### 三个阶段不要混淆

- **数据构建**：选择既有基准的长上下文样本；论文不是构造单元测试数据集。
- **压缩与推理**：压缩器评分并选代码片段；下游模型接收压缩提示后生成一次相应任务输出。压缩器可以和生成模型不同。
- **评估**：将生成结果与参考补全、参考摘要或目标函数匹配度比较；这些分数不是压缩器自身的准确率。

## 数据集与实验设置

| 任务／数据集 | 样本与筛选 | 平均上下文 Token | 平均参考输出长度 | 语言 |
| --- | --- | ---: | ---: | --- |
| Long Code Completion | 从测试集筛出 500 个上下文超过 5,000 Token 的 Python 示例 | 9,328.2 | 12.4 | Python |
| Long Module Summarization | 从 216 个样本中筛出超过 2,000 Token 的 139 个样本，来自 43 个仓库 | 10,809.6 | 1,758.1 | Python |
| RepoQA | 600 个长上下文问答测试、60 个仓库 | 11,524.6 | 156.0 | Python、Java、JavaScript、Rust、Go、C++ |

数据来自论文引用的 LongCoder、Long Code Arena 和 RepoQA 基准；数据统计见表 I（PDF 第 5 页）。

开源生成模型包括 DeepSeek-Coder-6.7B、Qwen2.5-Coder-7B、Seed-Coder-8B；闭源模型包括 GPT-4o 和 Claude-3.7-Sonnet。压缩模型与生成模型一致的设置用于主要实验，另做跨模型压缩实验。论文报告硬件为 Intel Xeon Gold 6254 CPU、NVIDIA A100 80GB（第 IV-C、IV-E 节）。

每个任务单独设预算：代码补全 2k Token、`R_fine=0.8`、`β=0.5`；摘要 5k、`R_fine=0.3`、`β=0.5`；RepoQA 2k、`R_fine=1.0`、`β=0.5`。作者称这些值由不与测试集重叠的小型 held-out 集确定（第 IV-E 节）。

## 指标：怎么算，说明什么

### 压缩比

```text
Ratio = 原始上下文 Token 数 / 压缩后上下文 Token 数
```

例如 4.3× 表示压缩后的上下文约为原文的 `1/4.3 ≈ 23.3%`，Token 减少约 76.7%。它只度量长度缩减，不单独表示代码正确性或质量。

### 代码补全

- **EM（Exact Match）**：生成补全与参考补全完全一致的样本比例，越高越好。
- **ES（Edit Similarity）**：基于生成与参考字符串编辑距离的相似度分数；表中按百分制报告，越高表示文本相似度越高，但不等于测试通过率。

### 模块摘要

用 GPT-4o-mini 作评审模型，把生成摘要和参考摘要连同代码一起比较，并将候选顺序反转提示两次。论文公式为：`CompScore = 1/2 [P(生成摘要胜参考) + (1 − P(参考胜生成))]`，按 0–100 报告，50 表示平均偏好相同（第 IV-D 节）。它是 LLM 评审的相对偏好分数，不是人工事实准确率。

### RepoQA

报告找到 needle function 的检索准确率：生成函数与目标函数的 BLEU 相似度超过 `0.8` 算命中，按百分比统计。它衡量函数复现／检索，不是单元测试执行成功率（第 IV-D 节）。

## 主要结果（逐条件记录）

- **Long Code Completion，Qwen2.5-Coder-7B，表 II**：LongCodeZip 的 ES 为 57.55、EM 为 32.40、压缩比为 4.3×；无压缩分别为 56.36、31.80、1.0×。同表 RAG（Function Chunking）为 ES 52.79、EM 26.00、3.1×。这些是该基准、该模型的结果，不能外推为测试补全表现。
- **Long Code Completion，Seed-Coder-8B，表 II**：LongCodeZip 为 ES 63.11、EM 37.40、5.6×；同模型无压缩为 ES 64.04、EM 40.20。故“无损”不适用于每个条件，压缩后的 ES、EM 在该项低于未压缩基线。
- **Long Module Summarization，DeepSeek-Coder-6.7B，表 III**：CompScore 28.01、压缩比 2.5×；无压缩 CompScore 19.09。该值是 GPT-4o-mini 评审分，不能与其他任务分数比较。
- **RepoQA，Qwen2.5-Coder-7B，表 IV**：平均准确率 87.2、压缩比 4.5×；无压缩准确率 86.0。各语言分数分别为 Python 92、C++ 78、Java 87、TypeScript 85、Rust 86、Go 95。
- **闭源模型，表 V**：GPT-4o 在 Long Code Completion 的 ES 为 64.72（无压缩 65.13），压缩比 4.3×；Claude-3.7-Sonnet 的 ES 为 66.27（无压缩 66.24），压缩比 4.3×。RepoQA 平均准确率方面，LongCodeZip 对 GPT-4o 为 88.9（无压缩 87.8），对 Claude 为 88.9（无压缩 89.7），并非两个模型上都超过无压缩。
- 作者报告主要压缩方法比较在 10 次重复实验上使用 Wilcoxon signed-rank test，称结果达到 `p < 0.001`（第 V-A 节）。这描述统计显著性，不自动意味着所有指标都有实质改善或“无损”。

## 消融与效率

**消融条件**：Long Code Completion、Qwen2.5-Coder-7B，表 VII（PDF 第 8 页）。完整方法 ES/EM 为 57.55/32.40，压缩比 4.3×。以同预算完整方法为基准：

- 把 AMI 排序换成相似度排序：ES 49.66、EM 25.20。
- 换成随机函数排序：ES 39.76、EM 11.50。
- 去掉细粒度压缩：ES 56.10、EM 31.20。
- 去掉自适应预算：ES 55.21、EM 29.40。
- 用逐行分块代替困惑度分块：ES 55.98、EM 31.20。
- 随机选择代码行：ES 55.07、EM 29.00。

在这个特定设置中，粗筛的条件困惑度排序影响最大；细粒度预算和块选择也带来增益。消融不能证明依赖组预算策略的价值，因为论文没有测试该机制。

**效率条件**：表 IX 只报告 Long Code Completion、Qwen2.5-Coder-7B 的代表性方法单次耗时。无压缩生成 15.70 秒；LongCodeZip 压缩 2.58 秒，生成 6.59 秒，压缩比 4.3×，ES/EM 57.55/32.40。表格并列列出压缩与生成时间，二者简单相加为 9.17 秒，比无压缩 15.70 秒少约 41.6%；这是根据表中数字计算的推论，不是作者单列的端到端统计，也不含所有可能的系统成本。论文报告 LongCodeZip 额外压缩 GPU 显存 0.69GB，生成阶段额外 0.81GB，生成基座模型参数显存为 28.37GB（第 V-D 节）。

## 作者解释、局限与应谨慎理解之处

### 作者解释

作者认为函数级 AMI 筛选去掉大量无关代码，细粒度阶段则在较高压缩率下保留关键内容；消融结果支持各模块在代码补全设置中的贡献。作者也承认：若上下文缺乏相关信息，或指令含糊、难以和上下文片段对齐，压缩器可能选不出有用块（第 VI-B 节）。

### 论文明确提到的效度威胁

- 摘要评测依赖 LLM judge，可能与专家评价不同，仍可能有顺序效应；作者用反序提示取平均缓解。
- 结果可能依赖特定数据集、语言和模型，尽管论文做了跨任务／模型评测。
- 训练数据泄漏风险；作者额外使用 2023 年 3 月以前训练的 DeepSeek-Coder-6.7B 作为一种缓解方式（第 VII 节）。

### 阅读者分析（不等于论文已证明）

- 论文把“片段让模型更好预测指令”作为相关性信号；AMI 能捕捉某些非词面关联，但没有显式构造“状态定义—更新—检查”依赖组，也没有保证几个必要片段共同进入最终上下文。
- 论文的块边界基于行困惑度变化，代码行切分对缩进、跨行表达式、类级状态和动态调用关系可能敏感。本文没有看到对“依赖闭包完整率”或静态依赖边召回率的评测。
- 表格中若干压缩条件仍低于无压缩基线（例如 Seed-Coder-8B 补全、Claude RepoQA）。所以更准确的总结是“多数压缩基线下有优势，若干条件接近或超过无压缩”，而非所有任务都不损失性能。
- 压缩器与生成器同模型的主要设置有利于任务条件评分；跨模型结果虽有展示，但不代表任意压缩器／生成器组合都稳定。
- 摘要、补全和 BLEU 阈值检索的评价维度不同；论文没有单元测试生成、测试运行、覆盖率或突变测试指标。

## 与当前研究方向的关系

当前方向文件聚焦：固定生成模型、以 Python 单元测试补全为主，在有限预算内保留代码细节与依赖关系，并比较压缩质量和成本。

### 可直接借鉴

1. **函数→代码块的层级粒度**：可作为压缩上下文的候选分层，不必把整份文件当作不可分割对象。
2. **同一预算下的质量—效率曲线**：比只报告压缩倍数更符合研究目标；报告输入 Token 与生成质量，并把压缩开销计入总成本。
3. **有解释力的消融**：比较依赖选择、统一精度、分块策略与背景压缩各自作用。
4. **直接基线**：LongCodeZip 的开源实现适配到 TestGenEval extra test completion；严格对齐允许的信息池、生成模型、输入预算和生成次数。原文得分只能作为背景，不能直接与本研究得分相减。

### 关键差别与可检验研究空缺

LongCodeZip 按条件困惑度给单个函数／块打分，并以函数重要性配额和块背包满足预算；你的方向进一步关心**多个代码单元能否组合成足以支持测试行为的依赖组**，以及每个成员只需保留接口、相关片段还是完整实现。可测试的差异是：同一 Token 预算下，“单元独立排序／LongCodeZip 式筛选”与“分级表示＋依赖组联合选择”相比，能否提高测试可执行比例和新增覆盖。

这只是研究设计上的关联和假设，不是 LongCodeZip 已经证明依赖组方案有效。可将 LongCodeZip 作为方法基线，但需说明原论文任务与 TestGenEval 任务不同，需重新适配并在共同样本上评测。

## 结论速记

LongCodeZip 的实质贡献是将条件困惑度驱动的函数级选择、函数内语义分块、自适应预算和背包选择组合成代码上下文压缩流程。论文对长代码补全、摘要和 RepoQA 给出多模型结果及消融；但其“依赖保持”主要通过模型条件相关性间接实现，没有显式评估依赖组完整性。对当前研究最有用的定位是：**层级压缩和效率评测的直接基线，也是依赖组联合预算方法需要超越／补足的对照方法。**

## 章节结构导读：每一章做了什么

1. **I. Introduction（引言）**：介绍长代码上下文带来的成本和信息定位问题，指出通用文本压缩、检索方法用于代码时的不足，并概述 LongCodeZip 的两阶段方案与论文贡献。
2. **II. Motivation（研究动机）**：通过配置类等例子说明，词面相似度可能找不到名称不相似、但对任务关键的代码，由此引出任务条件相关性评分的必要性。
3. **III. Methodology（方法）**：全文核心。先定义输入上下文、任务指令和 Token 预算，再介绍 AMI 评分、函数／类级粗筛、困惑度引导的函数内分块、自适应预算分配和 0/1 背包块选择。
4. **IV. Experimental Setup（实验设置）**：说明三类基准任务、样本筛选与数据统计，列出比较基线、开源和闭源模型、评价指标、各任务预算与实验硬件。
5. **V. Results（实验结果）**：报告主要任务结果，并分别分析消融、跨模型迁移和运行效率，回答方法是否有效、哪些组件有贡献、压缩是否节省下游成本。
6. **VI. Discussion（讨论）**：解释压缩率与下游表现的关系，给出细粒度压缩案例，并讨论模糊指令或缺少相关上下文时的失败情形及两阶段设计的使用取舍。
7. **VII. Threats to Validity（效度威胁）**：讨论摘要 LLM 评审、数据集／语言／模型覆盖范围，以及训练数据泄漏风险等可能影响结论的因素和作者采取的缓解办法。
8. **VIII. Related Work（相关工作）**：回顾代码语言模型、长上下文代码任务、提示压缩和代码检索方法，定位 LongCodeZip 与这些工作的联系和差异。
9. **IX. Conclusion（结论）**：概括两阶段代码压缩方法及论文报告的跨任务、跨模型结果与效率收益。
