# TestGenEval 阅读计划

**建议用 3 次、每次约 60 分钟完成。** 阅读时始终围绕一个问题：在 *extra test completion* 中，模型究竟看到了什么、生成了什么，以及一个补充测试怎样才算有效？

## 第一次：把任务说清楚（约 60 分钟）

读正文 **第 2.1–2.2 节**、图 2–5，再读**附录 C（Prompts）**。

先画出一条任务流程：代码文件与已有测试文件 → 提示词 → 生成一个新测试 → 插入并执行 → 评价。特别核对 `first`、`last`、`extra` 三种设置的区别。你的主任务是 `extra`：输入包含被测代码和**完整的已有测试文件**，目标是在看似完成的测试套件中再补一个测试。

读完应能回答：

1. 样本中的代码文件、测试文件如何配对和筛选？
2. `extra` 的提示词包含哪些内容？哪些内容属于你可以压缩的原始信息池？
3. 生成结果须满足什么格式？新测试如何接入已有测试？
4. 如果只压缩输入上下文，哪些任务说明和输出要求必须固定？

**本次产出：**写一页“`extra` 任务卡”，列出输入、输出、执行方式和不可改变的评测条件。

## 第二次：弄懂指标与实验难点（约 60 分钟）

读正文 **第 3.2 节**，重点看**附录 D.2.2（Test Completion Metrics）**和**附录 E.1.2、E.2.2** 中 `extra` 的完整结果；第 3.1 节只需了解整文件测试生成与补全任务的区别。

分清四个量：`pass@1`、`pass@5`、覆盖率增量，以及只在通过样本上统计的覆盖率增量。尤其要记住：**测试运行通过，不代表它覆盖了新的代码。** 论文中，已有测试较完整时，新测试通常很难增加覆盖率；作者也因计算成本和覆盖增量接近零，没有为测试补全报告变异分数。

**本次产出：**做一张指标表，每项写明“计算对象、失败样本如何处理、能说明什么、不能说明什么”。再写下你实验的主判断：同预算下，压缩方法是否提高有效测试比例和新增覆盖，而不只是缩短输入。

## 第三次：寻找与你的方法直接相关的证据（约 60–90 分钟）

读正文 **第 4.1.3 节**及**附录 F.4** 的上下文长度实验，再读**附录 F.5–F.7** 的错误分析与具体案例。最后浏览附录 A 的文件长度和仓库分布，以及论文的局限性。

重点追踪三类案例：

- **对象构造或测试准备失败：**生成测试缺少什么前提？前提位于代码、已有测试，还是两者之间？
- **依赖或状态理解错误：**模型是否看到了目标方法，却漏掉构造函数、状态更新或被调用对象的要求？
- **断言错误或重复测试：**是行为细节缺失，还是已有测试占据上下文后，模型只模仿了已覆盖路径？

对每个案例记录“缺失的信息 → 可能需要保留的依赖组 → 最低保留精度”。不要把论文的失败原因都归结为上下文不足：有些是模型推理或格式遵循问题，压缩方法未必能解决。

**本次产出：**挑 2–3 个案例，分别写出你会保留的原文条件、可缩成接口的信息，以及可去重的已有测试内容。

## 读完后的检查

如果你能不看论文解释以下四点，就可以开始做 Lite 样本，而无需反复通读全文：

1. `extra` 与 `last` 的输入差在哪里？
2. 为什么你的方法必须同时处理被测代码和已有测试？
3. 为什么要同时报告通过率与新增覆盖？
4. 论文只检验了“上下文长度”的哪些影响？你的“分级保留＋依赖组联合选择”准备检验什么额外问题？

随后选一个 TestGenEvalLite 样本，手工标出**目标调用、构造／fixture、状态条件、已有测试覆盖的行为**，做一版压缩前后上下文对照。这会比继续泛读结果表更快暴露方法设计上的问题。
